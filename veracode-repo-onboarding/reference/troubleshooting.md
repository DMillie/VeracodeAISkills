# Troubleshooting: symptom → cause → fix

Diagnose from the job log before re-running anything (rule 9). `[TS-nn]` = entry in the evidence register (`evidence/` in the source repository).

| Symptom | Cause | Fix |
|---|---|---|
| Pipeline not created / lint: `Component '…/veracode@X' - project does not exist or you don't have sufficient permissions` (or `Project … not found or access denied` for `include: project`) [TS-01] | the user who triggers the pipeline cannot read the central component project (private, user not a member). Includes use the user's permissions, not the job token | make the central project internal or add the consuming group as a member (Reporter); re-lint with a normal member's token |
| Lint: `Component '…@1.0' - content not found` / `@~latest` not found [TS-02] | partial versions and `~latest` need a catalog-published release; a release made through the Releases API is not one. Or the tag does not exist | pin the exact tag (`@1.0.0`), which is the rule anyway |
| Lint: `` `rollout_stage` input: `x` cannot be used because it is not in the list of allowed options `` or `app_name input: required value has not been provided` | a wrong or missing input on the include | fix the input; the component's README lists them |
| After adding the Veracode include the team's own included jobs disappeared, or lint says `unknown keys in extends` for an existing job [TS-03] | the CI file already had a top-level `include:`; a second `include:` key replaced it (YAML: last key wins) | add the component as another entry of the existing `include:` list |
| A release-point job (`veracode-policy-scan`) ran on a feature branch [TS-04] | `$CI_COMMIT_TAG =~ /^$/` is true when the variable is unset | component ≥ 1.0.0 guards every regex rule with `$VAR &&`; in own rules always write `$VAR && $VAR =~ /…/` |
| Job orange (allowed failure) with exit code 42 | the component's warning state: policy-violating flaws in stage `warn`; `block-new` without a baseline yet; policy scan Did Not Pass below `block-policy`; a tool error in `audit`/`warn`; profile not found in `veracode-policy-resolve` | read the `VERACODE GATE:` / `WARNING:` line; nothing to retry |
| `veracode-policy-resolve`: `application profile '<name>' not found (exact name)` | `app_name` input differs from the profile name, the profile was not created, or the API account cannot see it (team restriction) | create/rename with `tools/veracode_app_profile.py` (in the veracode-repo-onboarding skill), command `ensure`; fix the input |
| Pipeline Scan: `Builtin policies cannot be downloaded` in `.veracode-policy/request.log` [TS-05] | `--request_policy` only works for custom policies | nothing: the component then applies the built-in policy with `--policy_name` |
| `Veracode CLI … checksum mismatch` / `SCA agent archive checksum mismatch` | the pinned version's file changed upstream, a proxy altered it, or the version input was overridden without its SHA-256 | do not run it; re-pin with `tools/pin-versions.sh` (in the central component project) (checks the SCA PGP signature) and release a patch version |
| CLI or agent download 404 for a pinned version | Veracode removes old CLI versions from `tools.veracode.com` [TS-18] | mirror the tarballs internally and set `cli_download_url` / `sca_agent_download_url` in the central project |
| The team's later stages wait many minutes on main [TS-06] | `veracode-policy-scan` waits for the verdict in the stage given by `stage`, and later stages wait for it | component ≥ 1.1.0 runs the policy and sandbox scans in `.post` (input `release_stage`) |
| Pipeline Scan job: `artifact 'veracode-package.zip' not found` | the packaging job did not run on this ref (its `rules`), has another name than input `package_job`, or publishes another path than input `artifact` | make the packaging job run on every ref the Veracode jobs run on; align `package_job` / `artifact` |
| Pipeline Scan: `No files found for scanning` / "no supported modules" | wrong package: tests only, bundles, Go module at the zip root, .NET without PDBs | playbook/04; list the archive in the log |
| Pipeline Scan green with 0 findings on a real app | packaging problem, not a clean app | check the listing and the module list; compare with the CLI directory scan's view of the app |
| Pipeline Scan job red although you expected report-only | rollout stage is `block-new` (and a baseline exists) or `block-policy` | that is the gate working: see the `VERACODE GATE:` line and `filtered_results.json`; the stage is the `rollout_stage` input |
| Pipeline Scan: `Either the file 'results.json' does not have the correct file permissions` or `FileNotFoundException … (Permission denied)`, intermittently [TS-07] | the image runs as uid 1000 and the reused per-slot build volume is root-owned 0755 (created by a root-image job) | the component sets `image:docker:user: root` on the Veracode image jobs; or clear the runner's build volumes |
| Pipeline Scan `HTTP 401` | OAuth credentials in the HMAC variables, wrong region, expired key, clock skew | names only: confirm the variables hold the HMAC pair of the service account; check expiry on the Platform |
| Pipeline Scan `HTTP 403` | role missing (`greenlightapiuser`) | ask the Platform admin to add the role |
| Any Veracode job: variables empty in the job (`SRCCLR_API_TOKEN is not set`, `VERACODE_API_KEY_ID: unbound`) | variables are **protected** and the branch is not, or scoped to another environment, or defined on a different group | make them unprotected (masked is fine), or run on protected branches only |
| SCA agent: `There was a problem authenticating with Veracode SCA. Please double check your Veracode SCA agent credentials or the value of the env variable "SRCCLR_API_TOKEN".` (after ~2 min of silence) [TS-08] | the variable reaches the job but the Platform rejects the token: expired, revoked, wrong organisation, or a CLI activation token (36-char UUID) instead of a CI-type agent token | a user with SCA workspace rights creates a new CI-type agent token and replaces the variable; re-run the job. Meanwhile `veracode-cli-directory-scan` (on by default; HMAC only, direct dependencies) is the SCA coverage |
| SCA agent: `Invalid token` / 401 | token is a CLI activation token, not a CI-type agent token; or expired | a user with SCA workspace rights creates a CI-type agent token; an API service account cannot |
| SCA agent: `Unsupported architecture` | arm64 runner | `amd64/` image with platform linux/amd64 |
| SCA agent: no libraries found | package manager not in the image, or lockfile missing and build failed | use the language image (python:3.11, maven:…, node:18); run `npm ci` first for Node; add `--quick` to read lockfiles only |
| SCA agent: neither `curl` nor `wget` in the image | minimal image | use the project's real build image as `sca_image`, or install one via `sca_before_script` |
| Upload and Scan: `App not in state where new builds are allowed` | a policy scan is still open on the profile | `-deleteincompletescan 1` (already in the template), or delete the build on the Platform |
| Upload and Scan: a new profile appeared with a near-identical name | `-createprofile true` with a typo (not possible through the component, which always passes `false`) | create profiles by exact name with `tools/veracode_app_profile.py` (in the veracode-repo-onboarding skill) |
| Upload and Scan job green but no verdict | `policy_scan_timeout: '0'`: the job returned after upload ("SUBMITTED" in the log) | set the input to minutes to wait; otherwise report "submitted" |
| Upload and Scan stuck at `Pre-Scan Success` after a fatal pre-scan | `-deleteincompletescan 1` did not clear it [TS-09?] | `-action DeleteBuild` on that build, then re-run |
| Container scan: image "empty"/clean | scanned a `docker save` tarball | scan `name:tag` from the daemon |
| Container scan: `Cannot connect to the Docker daemon` | dind variables missing or host socket mounted | the four `DOCKER_*` variables from the template; runner mounts `/certs/client`; no socket mount |
| Container scan: `pull access denied` for `veracode/veracode-cli` | no such public image | the component downloads the pinned CLI tarball and checks its SHA-256 |
| CLI: `credentials undefined` | `~/.veracode/credentials` ini not read (2.55.0) | export `VERACODE_API_KEY_ID/SECRET` (CI variables already are) |
| CLI directory scan lists Go modules (`github.com/docker/docker`, `golang.org/x/net`, `stdlib`) in a non-Go repo [TS-10] | the CLI binary was installed into the scanned directory | install the CLI elsewhere (`/usr/local/veracode-cli`, as the template does) or scan a sub-directory |
| CLI directory scan prints only INF lines | table goes to `--output` file | `cat` the file (template does) |
| GitLab lint: `jobs config should contain at least one visible job` | linting a file of hidden jobs only | `GITLAB_LINT_PROBE=probe tools/gitlab-ci-lint.sh …` or lint the including `.gitlab-ci.yml` |
| GitLab lint: `local file ... not found` | `include: local:` (last-resort copy form) before the file exists on the ref | push the branch and lint with `GITLAB_LINT_REF` |
| Two pipelines per push after the change | you added `merge_request_event` rules next to branch-pipeline jobs | use branch rules like the examples, or (team decision) a `workflow:` rule |
| Baseline job: `could not publish the baseline package: HTTP 000` / `curl-error`, and MR jobs report `package: HTTP 000` [TS-11] | `CI_API_V4_URL` (from the instance's external URL) is not reachable from job containers | set a group/project variable `CI_API_V4_URL` to the hostname jobs can reach (e.g. `http://gitlab:8929/api/v4`) |
| MR job says "No baseline for 'main' yet" although `veracode-baseline` ran green on main [TS-12] | the fallback artifact URL needs a fully successful main pipeline; the package publish failed or the template is older than 2026-11-11 | check the baseline job log for "Baseline published: package …"; project packages must be enabled |
| Team's own later-stage job skipped after a Veracode job failed [TS-13] | failed job in an earlier stage, later job without `needs` | informational jobs carry `allow_failure: true` (template ≥ 2026-11-11); keep it |
| MR job says "No baseline on 'main' yet" forever | `veracode-baseline` never ran green on `main` (not merged yet, or its artifact expired and no newer run) | merge; run the main pipeline; the newest artifact of a ref is kept |
| Application profile create: HTTP 400 "team" | the service account has team restrictions and no team was given | pass `--team "<team>"`, or give the account `noteamrestrictionapi` |
| REST `/applications?name=` returns several | partial match | exact-name filter (the tool does) |
| Pipeline Scan: `PIPELINE-SCAN ERROR: CREATE FAILURE: HTTP Response 429: Too many requests ... 6 scans per minute` [TS-14] | the API user submitted more than 6 Pipeline Scans in a minute (one service account shared by many pipelines) | component >= 1.3.1 waits and retries; otherwise retry the job once after a minute. Ask for one API service account per team if it keeps happening |
| Pipeline Scan: `No files found for scanning`, exit 255 [TS-15] | the archive holds nothing the engine recognises in the layout it expects (source of a compiled language, a wheel, stripped binaries, files at the wrong depth) | read the language's packaging page; it is a packaging problem, never a clean result |
| Pipeline Scan green, `SUCCESS`, 0 or very few findings on a real application [TS-16] | wrong package (release build without debug info, obfuscated, minified or bundled output, extra files that change how the archive is read), OR right package and the engine does not follow this code (unsupported framework, library without an entry point, unsupported language accepted anyway) | playbook/04 "Few findings: package or engine?"; report which of the two it is and what is expected but missing |
| Policy scan Did Not Pass although the static findings do not violate the policy [TS-17] | SCA on the uploaded libraries or lockfile found vulnerabilities that violate the policy | read the detailed report; say "Did Not Pass because of N library findings"; do not remove libraries from the package to get a pass |
| Azure DevOps: `cp: target '...' is not a directory`, step `Veracode: take the packaged jar` orange, Pipeline Scan skipped, run still green [ADO-28] | the self-hosted agent reuses its workspace: an older jar from another run sits next to the new one and the glob matches both | empty the download folder before `- download: current`, require exactly one jar, print the listing (`examples/git-flow-java.after.yml`); read the step warnings, not the run colour |
| Azure DevOps: run `notStarted` or `inProgress` for a long time [ADO-29] | waiting for the single agent (10 to 30 minutes is normal on a shared pool), or for a permission gate | `ado.py run-wait <id>` says which; wait for the agent; only a permission gate needs a person |
| Azure DevOps: packaging step shows failed, the zip is fine [ADO-30] | `set -o pipefail` and a listing piped into `head -3`: `head` closes the pipe, the left side exits 141, the step exits 1 | no `... \| head -N` under pipefail: use `sed -n 1,3p` or drop pipefail for that line |
| `scan-check.js` says an expected module is missing for a Go package [ADO-31] | the engine names the module `GOLANG files within ...`; the name you passed is not in it | `--module GOLANG` |
